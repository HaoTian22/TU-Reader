# TU 交易规则（line_rules.json）说明

`line_rules.json` 是 TU（交通联合）交易的声明式规则文件，描述 **transit.db 装不下的城市级规律**：
到哪里查设备、交易实际属于哪个城市、公交线路号怎么从编码算出来。App 只执行固定步骤，规则文件里没有代码。

- 内置：`app/src/main/assets/data/line_rules.json`
- 线上：`https://assets2.haotian22.top/line_rules.json`（R2 对象键 `line_rules.json`），与 transit.db 并列、独立发布
- 解析 / 求值：`app/src/main/java/com/example/nfctransit/data/TuLineRules.kt`（文件头为权威格式说明）
- 设备匹配：`TransitData.resolveTuPlan`
- 校验 / 盖版本 / 上传：`tools/line_rules.py`（与 App 同一求值逻辑的 Python 实现）

## 1. 什么进规则，什么进库

| 放进 transit.db（tripreader-data CSV） | 放进 line_rules.json |
|---|---|
| 具名线路、站点、设备编码 | 查找目标：去哪个前缀桶 / 哪个城市查设备 |
| 少量线路编码（含公式的具名例外，4 位及以上） | 城市纠正：误写城市码、冲突码保留本城 |
| 需要拼接或命名的线路（宁波支线 703-4、苏州夜专） | 交通族覆盖（bus / rail） |
| | 整段编码 → 线路号的公式（东莞、天津、宁波、苏州、约 105 个城市的简单公式） |
| | 编码与库中站码的拼法（贵阳地铁：线路、站点字段不相邻） |

评分算法、深圳 5180 终端号派生、合肥地铁时钟这类逻辑写在代码里，不写进规则。

## 2. 一笔交易怎么走

```
TU 1E 旅程记录 (+ 同时间戳的 TU 0x18 钱包记录)
        │
        ▼
 ① 求解 Plan ── 按文件顺序跑所有「求解规则」（then 含 targets / city / family）
        │        命中的规则全部叠加，每一项取第一条给出它的规则
        │        都没给 targets 时：只查记录自身城市码这一个前缀桶
        ▼
 ② 设备匹配 ── TransitData 在 Plan 各目标内评分取优（overlap / stationPrefix / key）
        │
        ▼
 ③ 线路号 ── 只对「库没给出线路/站点」的公交记录：
              按 Plan 目标依次，取文件中第一条成立且数值有效的 line 规则（仅显示，无 lineId）
```

详情页 Match 行会标出参与的规则：`(SP Rule: 规则 id, …)`。

## 3. 记录坐标

条件、线路号、查找键都按**原始记录的大写 hex 串**取切片：

- `bytes: [a, b]` — 字节下标 [a, b)，内部折算成 hex 字符 [2a, 2b)
- `nibbles: [a, b]` — hex 字符（半字节）下标 [a, b)

TU 1E 常用位置：

| 字段 | bytes | nibbles | 说明 |
|---|---|---|---|
| 记录类型 | [0, 1] | [0, 2] | |
| 终端号 | [3, 9] | [6, 18] | 可含 FF 填充 |
| subtype | [9, 10] | [18, 20] | `01` 轨道，`02` / `13` 公交，其他不限制 |
| 线路站点字段 | [10, 17] | [20, 34] | 各城自定；反馈/CSV 里的 14 位编码就是这一段 |
| 城市码 | [32, 34] | [64, 68] | BCD，如 `5810` |
| 收单机构 | [34, 42] | [68, 84] | 如 `12273610FFFFFFFF` |

换算：README 里写的「线路站点字段第 m–n 位」（从 1 数）= nibbles `[19 + m, 20 + n]`。
例：贵阳「3–4 位」= `[22, 24]`，「7–8 位」= `[26, 28]`。

`"rec": "18"` 读与 1E 同一时间戳配对的 TU 0x18 记录；1E 已轮换掉、只剩 0x18 时 `1E` 缺失。

## 4. 文件格式（format 2）

```json
{ "format": 2, "version": "yyyyMMddHHmmss", "rules": [ Rule, ... ] }
```

### Rule

| 键 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 唯一；详情页标记用；在线版样本不符时按 id 回退内置同 id 规则 |
| `note` | 否 | 来源说明（不要提及第三方 App） |
| `when` | 二选一 | 条件列表，全部成立 |
| `any` | 二选一 | 条件组列表，至少一组全部成立 |
| `then` | 是 | 见下 |
| `samples` | 应有 | 实卡样本，加载时校验 |

### Cond（条件）

```json
{ "rec": "1E" | "18", "bytes": [a, b] | "nibbles": [a, b],
  "eq": "0101" | "in": ["0", "1"] | "regex": "^[01]" | "range": [lo, hi],
  "radix": 10 | 16, "not": false }
```

- 四种判断恰好写一种；`range` 按 `radix`（默认 10）解析成数值后比较，闭区间。
- 记录缺失、切片越界、切片含未知半字节 `?` 时条件**不成立**；加了 `not` 时反而成立。
  所以「不是公交 subtype」写成 `{"bytes": [9, 10], "in": ["02", "13"], "not": true}`，subtype 未知的部分样本也能通过。
- 特殊条件 `{"target": "6020"}` / `{"target": ["1270", ...]}`：只用于 line 规则，限定当前套用的目标码。

### Then

| 键 | 阶段 | 说明 |
|---|---|---|
| `targets` | 求解 | 查找目标列表，按序 |
| `city` | 求解 | 交易实际城市（标准码，用于显示/统计）；不影响查找 |
| `family` | 求解 | `bus` / `rail`，覆盖按 subtype 推断的交通族 |
| `line` | 线路号 | 库未给出线路/站点的公交记录显示的线路号 |

带 `{"target": …}` 条件的规则只能有 `line`。

### Target（查找目标）

```json
{ "prefix": "5880" | "city": "4610",
  "family": "bus" | "rail",
  "mode": "overlap" | "stationPrefix" | "key",
  "key": [[22, 24], [26, 28]],
  "types": ["城际"],
  "fallbackBelow": 8 }
```

- `prefix` = 设备前缀桶（device_code 前 4 位，即卡上写的码）。
- `city` = 按 city_id 查所有含该城 TU 设备的前缀桶，只取该城设备（前缀不可靠时用，如济宁设备在 3000 前缀）。
- `family` 覆盖本目标的交通族。
- `fallbackBelow: n` — 前面目标的最佳匹配长度 < n 时才查，命中即取代；第一个目标不能是 fallback。
- `types` 精确限定 transit_type，仅 `stationPrefix` / `key` 模式可用。

三种匹配模式：

| mode | 规则 | 适用 |
|---|---|---|
| `overlap`（缺省） | 设备码与线路站点字段的最长重叠评分（长度 → 字节对齐 → 起始位置 → 非 0 长度） | 绝大多数城市 |
| `stationPrefix` | 设备码去前缀后须是字段前 8 位的**前缀**，取最长 | 短码在字段内任意位置会误命中时（绍兴城际） |
| `key` | 设备码去前缀后须**等于**按 `key` 切片拼出的查找键；同键多行不猜 | 线路、站点字段不相邻（贵阳地铁） |

`key` 是 1E 记录的 nibbles 切片列表，按序拼接。任一切片缺失或含 `?` 时本目标不查（不会退回重叠评分）。

### Line（线路号）

固定名称：`"line": "机场大巴"`

公式：

```json
{ "rec": "1E", "nibbles": [a, b], "radix": 10 | 16,
  "ops": [["mod", 1000], ["div", n], ["add", n], ["sub", n], ["mul", n]],
  "min": 1, "max": n, "prefix": "专", "append": "路" }
```

切片按 radix 解析 → 依次运算（整除向零截断）→ 检查 min / max → 拼上前后缀。
解析失败或越界视为不成立，继续尝试下一条规则。

### Sample（样本）

```json
{ "1E": "<hex>", "18": "<hex>",
  "expect": { "city": "1620", "targets": ["8040"], "line": "747", "device": "8040…" } }
```

- 至少有 `1E` 或 `18` 其一；hex 必须大写。
- **只用真实卡记录**。只知道部分字段（如用户反馈只给了线路站点字段）时，其余半字节写 `?`，不要补造。
  1E 样本长度至少 68 个字符（要含到城市码）。
- `city` / `targets` / `line` 由 App 和工具在加载时校验；`device` 只由 `tools/line_rules.py` 对 transit.db 校验
  （设备存在、落在计划目标内、`key` 模式下查找键与设备码一致）。
- 样本按**全部规则整体求值**后比对，所以规则顺序会影响样本结果。

## 5. 兼容与发布

- `format` 不等于 App 支持的版本：整个文件忽略。format 只在语义不兼容时升级。
- 新能力用**新增键**（如 `mode: "key"` + `key`）：旧 App 遇到未知键 / 未知 mode 只丢弃该条规则，其余照常。
  所以依赖新能力的规则只对新版 App 生效，旧 App 维持原行为。
- 样本不符的规则被丢弃；在线版丢弃的规则按 `id` 回退内置同 id 规则（原位置）。
- App 在设置页「站名映射表更新」时尽力下载，与内置版取 `version` 较新者。

```bash
python tools/line_rules.py            # 校验：结构 + 样本 + transit.db 引用检查
python tools/line_rules.py --stamp    # 发版前盖版本
python tools/line_rules.py --upload   # 校验 + 盖版本 + 上传 R2
```

## 6. 新增规则流程

1. 先判断能不能进库：具名线路 / 站点 → tripreader-data CSV，不写规则。
2. 拿到实卡记录（至少是线路站点字段 + 城市码），按 §3 换算坐标。
3. 选位置：求解规则放在线路号规则之前；线路号规则是**文件顺序第一条成立者胜出**，
   某城要覆盖共享公式（`shared-*-line`）时，专用规则须写在共享规则前面。
4. 条件尽量窄：只覆盖样本能证明的编码范围，例外排除掉，不外推。
5. 写样本 → `python tools/line_rules.py` → `gradle :app:testDebugUnitTest`（含「内置规则全部加载并通过样本」）。
6. 发版前 `--stamp`，需要线上生效时 `--upload`。

## 7. 示例

### 贵阳地铁：线路、站点不相邻（key 模式）

反馈：城市 7010，线路站点字段 `05010117000000` = 1号线 中山西路（库码 `70100117`）。
字段第 3–4 位 `01` 是线路，第 7–8 位 `17` 是站点。默认重叠评分里 `0101`（窦官）和 `0117`（中山西路）
同长且都字节对齐，会取错站。

```json
{ "id": "guiyang-metro",
  "when": [
    {"rec": "1E", "bytes": [32, 34], "eq": "7010"},
    {"rec": "1E", "bytes": [9, 10], "in": ["02", "13"], "not": true}
  ],
  "then": {"targets": [
    {"prefix": "7010", "family": "rail", "mode": "key", "key": [[22, 24], [26, 28]]},
    {"prefix": "7010", "family": "rail", "mode": "key", "key": [[22, 24]], "fallbackBelow": 4}
  ]},
  "samples": [{"1E": "????????????????????05010117000000…7010…",
               "expect": {"city": "7010", "targets": ["7010", "7010"], "device": "70100117"}}] }
```

第二个目标在站点不在库时退到 2 位线路行（`701001` = 1号线），不按重叠猜站。

### 广安邻水公交：带前后缀的线路号

反馈：城市 6690，`EA62…` = 邻水2路，`EA66…` = 邻水6路。6690 原本落在共享公式 `shared-dec4-tail-line`
（line[4..8]），对这类编码得 0 → 无线路，所以专用规则写在它前面。只覆盖 `EA61`–`EA69`，
10 路以上的编码没有样本，不外推。

```json
{ "id": "guangan-linshui-line",
  "when": [{"target": "6690"}, {"rec": "1E", "nibbles": [20, 23], "eq": "EA6"}],
  "then": {"line": {"rec": "1E", "nibbles": [23, 24], "radix": 10, "min": 1, "max": 9,
                    "prefix": "邻水", "append": "路"}} }
```

### 东莞：整段编码 → 线路号

线路站点字段 `0747 0101 5930`：首位 0/1 + 三位路号 + `0101` → 747。

```json
{ "when": [{"target": "6020"}, {"rec": "1E", "nibbles": [20, 21], "in": ["0", "1"]},
           {"rec": "1E", "nibbles": [24, 28], "eq": "0101"}],
  "then": {"line": {"rec": "1E", "nibbles": [21, 24], "radix": 10, "min": 1}} }
```
